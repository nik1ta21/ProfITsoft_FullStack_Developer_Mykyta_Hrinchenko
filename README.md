# Програма статистики відеоігор

Консольна програма, яка парсить JSON-файли з відеоіграми з указаної папки та формує XML-файл зі статистикою за одним із атрибутів. Файли парсяться потоково (без завантаження файлу цілком у пам'ять), кожен файл обробляється в окремому завданні пулу потоків.

## Предметна область

Дві сутності зі зв'язком багато-до-одного:

- **Game** (основна сутність) — відеогра: `title`, `developer`, `year_released`, `genre`.
- **Developer** (другорядна сутність) — розробник гри, має `name`. Багато ігор посилаються на одного розробника.

### Атрибути Game у JSON

| Атрибут         | Тип     | Опис                                                                  |
|-----------------|---------|-----------------------------------------------------------------------|
| `title`         | String  | назва гри                                                             |
| `developer`     | String  | назва розробника (у коді перетворюється на `Developer`)               |
| `year_released` | Integer | рік випуску                                                           |
| `genre`         | String  | кілька жанрів через кому, наприклад `"RPG, Action Adventure"`         |

Статистику можна формувати за `developer`, `year_released` та `genre` (текстовий атрибут із кількома значеннями).

## Структура проєкту

```
src/main/java/com/profitsoft/gamestats/
├── GameStatisticsApplication.java        # точка входу, розбір аргументів
├── model/
│   ├── Game.java                         # основна сутність (record)
│   └── Developer.java                    # другорядна сутність (record)
├── parser/
│   └── GameJsonParser.java               # потоковий парсинг одного файлу (Jackson)
├── statistics/
│   ├── StatisticAttribute.java           # enum атрибутів: назва + як отримати значення з гри
│   ├── StatisticsCalculator.java         # лічильники значень, злиття, сортування
│   ├── StatisticItem.java                # пара «значення — кількість»
│   └── DirectoryStatisticsProcessor.java # пул потоків: файл = завдання
├── xml/
│   └── XmlGenerator.java                 # запис результату в XML
└── benchmark/
    ├── DataGenerator.java                # генерація великих JSON-файлів для експерименту

src/main/resources/sample-data/           # невеликі приклади вхідних файлів
src/test/java/...                         # unit-тести
```

## Вимоги

- Java 21
- Maven 3.x

## Збірка і тести

```bash
mvn clean test
```

## Запуск

```bash
mvn exec:java "-Dexec.args=<directory> <attribute> [threadCount]"
```

- `directory` — папка з JSON-файлами (обробляються файли `*.json` безпосередньо в ній);
- `attribute` — `developer`, `year_released` або `genre`;
- `threadCount` — кількість потоків для парсингу (необов'язково, за замовчуванням 1).

Приклади:

```bash
mvn exec:java "-Dexec.args=src/main/resources/sample-data genre 4"
mvn exec:java "-Dexec.args=src/main/resources/sample-data developer 2"
mvn exec:java "-Dexec.args=src/main/resources/sample-data year_released"
```

Результат записується в `statistics_by_{attribute}.xml` у поточній папці. Некоректний атрибут або кількість потоків відхиляються одразу, до початку парсингу.

## Формат вхідних файлів

Кожен файл — JSON-масив ігор (`src/main/resources/sample-data/games1.json`):

```json
[
  {
    "title": "The Witcher 3: Wild Hunt",
    "developer": "CD Projekt Red",
    "year_released": 2015,
    "genre": "RPG, Action Adventure"
  },
  {
    "title": "Cyberpunk 2077",
    "developer": "CD Projekt Red",
    "year_released": 2020,
    "genre": "RPG, Action, Open World"
  }
]
```

Правила обробки даних:

- пропущене поле, `null` або значення неправильного типу не потрапляють у статистику (гра при цьому враховується в загальній кількості оброблених ігор);
- `year_released` у вигляді рядка `"2015"` приймається;
- жанри обрізаються від пробілів, порожні й повторювані жанри в межах однієї гри відкидаються; регістр зберігається («RPG» і «rpg» — різні значення);
- невідомі поля, зокрема вкладені об'єкти й масиви, пропускаються;
- файл, що не є JSON-масивом об'єктів або містить синтаксичну помилку, завершує програму з повідомленням, у якому названо файл.

## Формат вихідного файлу

Результат для `src/main/resources/sample-data` за атрибутом `genre` (`statistics_by_genre.xml`), відсортований за кількістю від більшого до меншого, при однаковій кількості — за значенням:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<statistics>
  <item>
    <value>Action</value>
    <count>5</count>
  </item>
  <item>
    <value>Open World</value>
    <count>5</count>
  </item>
  <item>
    <value>RPG</value>
    <count>4</count>
  </item>
  ...
</statistics>
```

## Як це працює

1. `DirectoryStatisticsProcessor` знаходить `*.json` файли папки й відправляє кожен у `ExecutorService` з фіксованим пулом потоків.
2. Завдання парсить свій файл через `GameJsonParser`: Jackson читає токени, а кожна гра одразу передається в `StatisticsCalculator` цього завдання. Ігри не накопичуються, тому пам'ять не залежить від розміру файлів.
3. Калькулятори окремих файлів зливаються в один, результат сортується й записується в XML.

## Експерименти з кількістю потоків

Дані й заміри:

```bash
# 1. Згенерувати 8 файлів по 200 000 ігор (≈ 23 МБ кожен, у папку data/, яка ігнорується git)
mvn compile exec:java "-Dexec.mainClass=com.profitsoft.gamestats.benchmark.DataGenerator" "-Dexec.args=data/large 8 200000"

# 2. Заміряти час для 1, 2, 4 і 8 потоків (1 прогрів + 5 вимірів на кожну кількість потоків)
mvn compile exec:java "-Dexec.mainClass=com.profitsoft.gamestats.benchmark.ThreadBenchmark" "-Dexec.args=data/large genre 5"
```

Вимірюється повний час обробки (парсинг усіх файлів і підрахунок), без запису XML.

### Результати

**Умови:** 8 файлів по 200 000 ігор (≈ 23 МБ кожен, разом ≈ 184 МБ, 1,6 млн записів), атрибут `genre`, Java 21, 16 логічних процесорів (`Runtime.availableProcessors()`). Для кожної кількості потоків: 1 прогрів (не враховується) і 5 вимірів.

| Потоки | Середній час, мс | Мін, мс | Макс, мс | Прискорення відносно 1 потоку |
|--------|------------------|---------|----------|-------------------------------|
| 1      | 1507             | 1459    | 1554     | 1,0×                          |
| 2      | 790              | 773     | 807      | 1,9×                          |
| 4      | 438              | 426     | 446      | 3,4×                          |
| 8      | 316              | 297     | 326      | 4,8×                          |

**Висновки:**

- Обробка добре масштабується: 2 потоки дають майже подвійне прискорення (ефективність ≈ 95 %), 4 потоки — 3,4× (≈ 86 %), 8 потоків — 4,8× (≈ 60 %).
- Приріст зменшується зі зростанням кількості потоків. Ймовірні причини (не перевірялись окремо): 16 логічних процесорів зазвичай означають менше фізичних ядер із hyper-threading, а також зростає навантаження на пам'ять і збирач сміття, бо кожна гра створює кілька об'єктів.
- Паралелізм у програмі виконується на рівні файлів, тому для 8 файлів корисні щонайбільше 8 потоків: пул із 16 потоків не дасть виграшу, бо завдань лише 8. Також найдовший файл обмежує мінімально можливий час.
- Розкид між прогонами малий (≈ 5 %), результати стабільні.
- Після прогріву файли, імовірно, лежать в кеші операційної системи, тому замір показує швидкість парсингу й підрахунку, а не диска.
- На маленьких файлах (кілька КБ) різниці між кількістю потоків немає: час визначається запуском JVM і витратами на створення пулу.
